2. LCEL INTERNALS: THE RUNNABLE PROTOCOL
================================================================================

All components in LCEL implement the abstract `Runnable<RunInput, RunOutput, CallOptions>`
interface. This unified contract provides four standard invocation modes:

1. `invoke(input, options)`:
   - Synchronous or asynchronous single-input execution.
   - Traverses the Directed Acyclic Graph (DAG) sequentially or in parallel.

2. `batch(inputs, options)`:
   - Evaluates a batch of inputs concurrently.
   - Can throttle parallelism with `options.maxConcurrency`.
   - Avoids spinning up unbounded event-loop promises.

3. `stream(input, options)`:
   - Returns an `AsyncIterableIterator<RunOutput>`.
   - Propagates chunked outputs backwards up the chain as soon as each node yields.
   - For LLMs, returns `AIMessageChunk` streams with delta content.

4. `transform(generator, options)`:
   - Enables stream-in / stream-out processing across runnables.

Composition Operators:
• `Runnable.pipe(nextRunnable)` / `RunnableSequence`:
  Passes the resolved output of node N as input to node N+1.
• `RunnableParallel` / `RunnableMap`:
  Takes a map of runnables `{ keyA: runnableA, keyB: runnableB }` and runs all keys
  concurrently with `Promise.all()`, returning `{ keyA: resA, keyB: resB }`.
• `RunnablePassthrough` & `RunnablePassthrough.assign`:
  Allows passing input through unchanged or appending new computed keys into the state object.
• `RunnableLambda`:
  Wraps any plain JavaScript/TypeScript function `(input) => output` into a fully-fledged
  Runnable supporting `.invoke()`, `.batch()`, and `.stream()`.
• `withFallbacks([fallbackRunnable1, fallbackRunnable2])`:
  Wraps a target runnable in a try-catch failover mechanism that intercepts exceptions
  and delegates execution to backup runnables.

4. DEBUGGING PLAYBOOK: SLOW AND OPAQUE CHAINS
================================================================================

When an LCEL chain is underperforming or behaving unexpectedly in production:

Symptom 1: Chain has high latency, but LLM generation time is low.
Diagnostic Strategy:
1. Attach an `InMemoryMetricsTracer` callback to record the exact start/end time of every runnable.
2. Check for sequential bottlenecks: Are independent fetch operations running in `pipe()`
   instead of `RunnableParallel`?
3. Check for heavy synchronous transforms in `RunnableLambda` blocking the Node.js event loop.

Symptom 2: First-Token-Latency (TTFT) is massive despite using .stream().
Diagnostic Strategy:
1. Identify any intermediate Runnable that does not implement `transform()`. If a step buffers
   its entire input before yielding, downstream streaming is completely blocked.
2. Ensure output parsers support streaming (`StringOutputParser` or incremental JSON parsers)
   rather than whole-payload JSON.parse.

Symptom 3: Obscure stack trace inside LangChain internal runner.
Diagnostic Strategy:
1. Decompose the chain: Replace `.pipe()` chains with an explicit step-by-step unrolled harness:
   ```ts
   const step1 = await runnable1.invoke(input);
   console.log("Step 1:", step1);
   const step2 = await runnable2.invoke(step1);
   ```
2. Inspect input/output contracts between adjacent runnables to identify schema mismatches.

When to rip out LangChain for raw code:
• The chain has fewer than 3 linear steps without dynamic provider switching.
• Ultra-low latency is required (sub-20ms SLA where LangChain's 5-15ms overhead is >25% of total budget).
• The team requires fine-grained abort control, explicit custom sockets, or zero external framework dependencies.
